# Professional Review Boundary Checklist

This checklist exists to protect the integrity of the platform’s claims.

## Software May Claim
- [ ] Detection of known critical geometric / topological defects (adversarial suite)
- [ ] Deterministic evaluation of a published rule-pack version
- [ ] Reproducible reports given the same inputs and engine commit
- [ ] Clear separation of authoritative geometry vs presentation layers
- [ ] Explicit `REVIEW_REQUIRED` / `BLOCKED` / `INCOMPLETE` states

## Software Must Never Claim
- [ ] Automatic construction readiness
- [ ] Automatic permit or sanction readiness
- [ ] Automatic fire / life-safety certification
- [ ] Automatic structural adequacy
- [ ] Automatic accessibility (RPwD) final compliance without human review
- [ ] Replacement of licensed architect, structural engineer, MEP, fire consultant, surveyor, or local authority

## Process Requirements Before Any “Issuable” Stamp
- [ ] Independent professional review completed (minimum two reviewers for critical packages — align with existing Week 24 intent)
- [ ] Site survey confirmation of critical assumptions (frontage, setbacks, levels)
- [ ] Local bylaw and authority review path identified
- [ ] Rule-pack version and engine commit recorded on the issued package
- [ ] Known limitations register attached

## UI / API Copy Rules
- Prefer language such as:
  - “Validated for preliminary review”
  - “Requires professional sign-off”
  - “Not a construction or permit document”
- Avoid language such as:
  - “Approved”
  - “Code compliant — ready to build”
  - “Certified”
